## 二、P1（上线体验与数据可靠性）

| # | 项目 | 状态 | 实现位置 | 说明 |
|---|---|---|---|---|
| 1 | **每日数据同步可靠性** | **本次新增** | `services/dailySync.ts` | 原 Hermes cron（`0 2 * * *`）在容器环境从未执行过（`last_run_at` 恒为 null）。改为进程内 30 分钟检查一次，仅当 `real-fixtures.json` 的 `generatedAt` 变化时才重建 |
| 2 | **同步误删业务数据隐患** | **本次修复** | 同上 | 首版实现按「距上次同步超 24h」无条件重跑 `seedDemoData`，而该函数会 `deleteMany` 全部业务表 → 每日会把用户新建的任务/项目/政策清空。已改为「只在数据版本变化时重建」 |
| 3 | **运行时指标端点** | **本次新增** | `GET /api/system/metrics` | 返回 uptime / RSS / heap / DB 体积 / 备份份数 / AI 降级率 / 自检结论 |
| 4 | 静态资源缓存策略 | 原已有 | `index.ts` 的 `setHeaders` | `/assets/**` 内容 hash 文件名 → `max-age=31536000, immutable`；其余 → `no-cache` 协商 |
| 5 | 数据库索引 | 原已有 | `schema.prisma` | `@@index` 共 12 处 |
| 6 | 前端产物就绪校验 | **本次新增** | 纳入启动自检 | API 活着但 `public/index.html` 缺失 = 界面白屏，这类故障靠自检提前拦住 |
| 7 | 请求/连接超时 | **本次新增** | `index.ts` 的 fastify 配置 | `connectionTimeout=30s`、`requestTimeout=60s`，避免慢客户端长期占连接 |

## 三、明确未做 / 做不了（需拍板或补充条件）

| 项目 | 结论 | 原因 |
|---|---|---|
| 外部告警通道（短信 / 钉钉 / 企业微信 / 邮件） | **做不了** | 无任何第三方告警凭据。当前以「启动自检日志 + `/api/system/selfcheck` 主动拉取」替代。若需推送，请提供 webhook 地址与鉴权方式 |
| HTTPS 证书生命周期管理 | **不需要本项目做** | 由 Cloudflare 边缘终止 TLS 并自动续期，源站走隧道明文回源 |
| MFA / 二次验证 | **未做** | 需求说明书未提出；工作量与账号初始化流程改动较大，需单独立项 |
| 备份恢复演练 | **未做** | `tools/backup_db.mjs` 可还原，但演练需要停服切换库文件；建议在正式上线前的维护窗口执行一次 |
| tsc 类型债（`seed-data.ts` 的 `Record<string, any>`、`rootDir`、`esModuleInterop`） | **未清理** | 既存问题，不影响编译产物输出与运行。若 CI 以 `tsc` 零错误为门禁，需单独安排 1–2 天清理 |
| 首屏 1.09s 公网实测 | **仍是估算值** | 需 Cloudflare API Token 才能从外部测速；本地与压缩比已实测（1.84MB → br 444KB） |

依赖版本约束（踩坑记录）：`@fastify/rate-limit` 必须用 **v9**（依赖 `fastify-plugin@^4`）配 Fastify 4；
v10 是 Fastify 5 专属，装上去会静默失效——与 `@fastify/compress` v9 是同一个坑，判据是**功能完全不生效但无任何报错**。
